# Trade Consumer (`TradeConsumer`)

The `TradeConsumer` is a dedicated, real-time worker class running within the `mdg-trade-group` Kafka consumer group. It is responsible for subscribing to matched trade execution streams and immediately forwarding them to the client-facing distribution layer.

By isolating trade streams in a dedicated consumer group separate from the [[entities/order-book-consumer|Order Book Consumer]], the Market Data Gateway (MDG) ensures that high-velocity trade executions are processed concurrently, maintaining independent scalability and protecting trade ticks from being blocked by large L2 order book snapshot updates.

---

## Responsibilities

The `TradeConsumer` manages the lifecycle and flow of trade execution events with the following core responsibilities:

*   **Kafka Stream Ingestion:** Establishes and maintains a high-availability connection to the [[entities/kafka-message-bus]] using the `kafkajs` library.
*   **Topic Subscription:** Subscribes to the [[ap:kb-order-management-system-order-matching-engine/summaries/order-matching-engine#nte-trades-matched|order-matching-engine (nte.trades.matched)]] topic, consuming events emitted by the upstream [[entities/order-matching-engine]].
*   **Decoupled Delivery Pipeline:** Operates asynchronously as part of the [[concepts/data-flow-pipelines|Path B: Trade Executions Pipeline]], isolating the matching engine core from client network issues (see [[decisions/decoupling-via-pub-sub]]).
*   **Downstream Hand-off:** Forwards raw message payloads directly to the [[entities/client-manager]] (`ClientManager.broadcastTrade()`) to trigger real-time [[concepts/websocket-egress|WebSocket broadcasts]].

---

## Dependencies

The `TradeConsumer` integrates with several internal and platform-wide components:

*   **Upstream Publisher:** [[entities/order-matching-engine]] via the external event topic [[ap:kb-order-management-system-order-matching-engine/summaries/order-matching-engine#nte-trades-matched|nte.trades.matched]].
*   **Message Broker:** [[entities/kafka-message-bus]] hosting the message partitions.
*   **Downstream Egress:** [[entities/client-manager]] (`ClientManager`) which maintains active WebSocket connections to external clients.
*   **Data Models & Schemas:**
    *   `nte.marketdata.TradeTick` defined via [[entities/protobuf-schema]] (`protos/market_data.proto`).
    *   Internal representation of `TradeEvent` defined in `src/models/types.ts`.
    *   See [[decisions/protocol-translation]] for the trade-offs of converting these schemas from Protobuf ingress to JSON egress.

## Implementation Details

The consumer is implemented in `src/consumers/TradeConsumer.ts` and initialized during the system boot phase in `src/index.ts`.

### Source Code (`src/consumers/TradeConsumer.ts`)

```typescript
import { Kafka } from 'kafkajs';
import { ClientManager } from '../websockets/ClientManager';

export class TradeConsumer {
    private kafka = new Kafka({ 
        clientId: 'mdg-trade-consumer', 
        brokers: [process.env.KAFKA_BROKERS || 'localhost:9092'] 
    });
    private consumer = this.kafka.consumer({ groupId: 'mdg-trade-group' });

    constructor(private clientManager: ClientManager) {}

    async start() {
        await this.consumer.connect();
        // Consuming trades generated by astrophage/order-matching-engine
        await this.consumer.subscribe({ topic: 'nte.trades.matched', fromBeginning: false });

        await this.consumer.run({
            eachMessage: async ({ message }) => {
                const tradeData = message.value?.toString();
                if (tradeData) {
                    this.clientManager.broadcastTrade(tradeData);
                }
            }
        });
    }
}
```

### Runtime Configuration

The configuration parameters are supplied via environment variables in the application topology (`docker-compose.yml`):

*   **Consumer Group ID:** `mdg-trade-group`
*   **Target Topic:** [[ap:kb-order-management-system-order-matching-engine/summaries/order-matching-engine#nte-trades-matched|order-matching-engine (nte.trades.matched)]] (or overriden via the `TRADES_TOPIC` environment variable)
*   **Broker List:** Configured via `KAFKA_BROKERS` (defaults to `localhost:9092` locally, or `kafka1.nte.internal:9092` in production)

## Data Pipelines & Flow

The `TradeConsumer` acts as the primary translator in **Path B (Trade Executions)** of the MDG [[concepts/data-flow-pipelines|Data Flow Pipelines]]:

```
[Order Matching Engine]
          │
          │ (Publishes binary TradeTick proto)
          ▼
[Kafka Topic: nte.trades.matched]
          │
          │ (Polled by TradeConsumer in 'mdg-trade-group')
          ▼
  [TradeConsumer]
          │
          │ (Hands off trade data string)
          ▼
  [ClientManager] ───► (Broadcasts L2 JSON TRADE_TICK payload) ───► [External Clients]
```

1.  **Ingestion:** The consumer retrieves execution data directly from the partition.
2.  **Conversion:** Currently, the system routes the string payload to the [[entities/client-manager]] where it is prepared for egress.
3.  **Broadcast:** The data is packed inside a `TRADE_TICK` WebSocket envelope and sequentially broadcast to all active subscribers via [[concepts/websocket-egress]] (incorporating design considerations documented in [[decisions/sequential-broadcast-fairness]]).

## Telemetry & Monitoring

Because trade updates are crucial for external charting systems and compliance auditing (e.g., the `compliance-surveillance-monitor` system), the consumption rate and lag on the `mdg-trade-group` consumer group are strictly monitored. Lag on the [[ap:kb-order-management-system-order-matching-engine/summaries/order-matching-engine#nte-trades-matched|order-matching-engine (nte.trades.matched)]] topic directly impacts the real-time accuracy of external clients' execution feeds and must be minimized to sub-millisecond levels under normal operating conditions.
